# ADR-007: 摄取并发闸 + 进度落库轮询（并发能力收敛第一步）

- 状态: 已接受
- 日期: 2026-09-08
- 相关: ADR-003（切块策略，摄取链路）

## 背景

单进程 FastAPI 全异步、同步 IO 均已 offload（to_thread），但并发能力有两处缺口：

1. **文档摄取无界**：`POST /upload` 每篇文档 spawn 一条 `BackgroundTasks` 流水线
   （embedding + LLM 抽取 + Neo4j/Chroma/SQLite 写）。突发批量上传会同时起 N 条流水线，
   打穿 provider 限流与 SQLite 写竞争——内部只有 per-provider 闸（embedding Semaphore(5)），
   没有流水线级全局闸。
2. **SSE 进度是进程内存状态**：进度事件只推给本进程 `asyncio.Queue` 订阅者。一旦部署
   多 uvicorn worker，上传落在 worker A、进度 SSE 连到 worker B 即收不到事件
   （history 接口走 DB 因此不受影响）。即「进程内状态 × 多进程」的经典错配。

## 决策

1. **摄取并发闸**：新模块 `services/ingest_gate.py` 提供进程级 `asyncio.Semaphore`，
   size 取配置 `DOC_INGEST_CONCURRENCY`（默认 2）。`process_document_background` 改成
   `async with get_ingest_gate():` 包住原流水线。排队期间文档保持 `pending`、不发进度，
   状态语义不变。
2. **进度落库轮询**：删除 ProgressEmitter 的进程内存订阅队列。每次进度事件把完整
   `data` payload 以 JSON 存入 `progress_history.payload_json`（守卫式 ALTER 加列，
   仿 documents.status 先例）；SSE 端点改为先回放历史、再按 `PROGRESS_POLL_SECONDS` 轮询
   新行，遇 complete/error 终止。SSE 帧结构、鉴权、前端零改动。

> 为什么必须把完整 payload 落库：前端进度弹层靠 `event.data.stage / entities /
> relations_sample` 路由与渲染，而 progress_history 原有列只存 percent/error/计数。
> 若只轮询原列，SSE 无法逐字复现事件，弹层会卡住。

## 后果

- 正面:
  - 突发批量上传由「N 条流水线同时打爆限流」变为「有界并发 + 排队」，可控、可观测；
  - SSE 进度从进程内存中解放——断线/换 tab/重连可回放已发生阶段；多 worker 下跨进程正确；
  - 零新依赖、无 Redis、前端零改动。
- 负面:
  - 进度事件实时性从「即时」降为「轮询间隔内」（默认 1s，可配）——embedding/LLM 阶段
    长达数秒，体感无差；
  - 进度读路径多一条带索引的 SELECT/秒（已加 `idx_progress_history_doc`）；
  - 排队的后台任务各自持有 markdown 字符串，极端批量大文档时占内存（记为开放项）。
- 取舍:
  - 未做「专用持久摄取队列」（上传只入队、worker 消费 pending）：对个人规模改动过大；
    doc_status 状态机本就可断点续传，未来要演化成队列时再立项。多 worker 化本身（含 BM25
    跨进程一致性）也未在本 ADR 范围，仅文档化约束（见 README「多 worker 部署须知」）。
