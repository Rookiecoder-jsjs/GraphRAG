# ADR-009: 并发扩容与质量保障——KeyPool + 查询嵌入合批 + 查询闸

- 状态: 已接受
- 日期: 2026-09-10
- 相关: ADR-007（摄取并发闸，并发能力收敛第一步）、GUIDE-002（评测基线）

## 背景

检索路径在高并发下有两个结构性短板，以及一个质量侧的隐性风险：

1. **查询嵌入放大 + 低并发上限**：`retrieve()` 对去重后的查询列表（rewrite + ≤3 个
   变体）逐条调 `embed_single`——一次搜索烧 1+N 次独立 `/embeddings` 请求；全服务
   embedding 并发被 `Semaphore(5)` 封顶（约 10–25 条/秒）。摄取路径批大小仅 5，
   300 chunk 的文档要发 60+ 次请求。
2. **重试策略浪费且低效**：embedding 用固定延迟 `[1,2,4,8,16]s`（无抖动，重试期间
   白占 semaphore 槽位）；全库从不读 429 的 `Retry-After` 头；多 key 场景下同一把 key
   撞 429 后干等，其余 key 闲置。
3. **缓存连接开销**：embedding 缓存读写每次新建 aiosqlite 连接（每连接一个线程），
   一次 300 chunk 摄取开关 ~600 次连接。
4. **过载即全员降级**：检索各环节（rewrite/变体/实体抽取/图谱通道/rerank）失败静默
   降级。低负载时几乎不触发；高负载时 429/超时增多，降级分支集体触发，但响应仍是
   200——用户无感地拿到"少了图谱通道、没经过重排"的结果。

约束（讨论确认）：**并发优化不得以检索质量为代价**；用户可提供多个 SiliconFlow key
（同 provider，embedding 模型维度一致才能共用同一个 Chroma collection）。

## 决策

1. **KeyPool**（`services/key_pool.py`）：`SILICON_FLOW_API_KEYS` 逗号分隔多把 key，
   embedding + rerank 共用；least-inflight 选择 + 每 key 在途上限 +
   429 冷却（读 `Retry-After`，钳到 `SILICON_FLOW_KEY_LEASE_TIMEOUT`）+ 有空闲 key 时
   **不 sleep 立即 failover**。`SILICON_FLOW_API_KEYS` 为空回退单 key，现有 `.env` 不动。
   LLM（Bailian）不在池内。
2. **查询嵌入合批**：`retrieve()` 改走 `embed_batch(queries)`——1+N 次请求 → 1 次；
   全有全无（与原全失败结局一致，同时移除"逐变体静默丢弃"这一负载下的召回损失）。
   `EMBED_BATCH_SIZE` 5 → 32（配置化）。批处理质量中性由 live 一致性测试背书
   （单发 vs 批发余弦 ≥0.999，`test_embedding_live_consistency.py`，opt-in）。
3. **共享缓存连接**：embedding 缓存改进程级共享 aiosqlite 连接（与 `get_db` 相同
   PRAGMA），批量读（`IN`）+ 批量写（`executemany`），表缺失降级为全 miss。
4. **查询闸**（`services/query_gate.py`，`asyncio.Condition`+计数器，规避 Python 3.11
   Semaphore 取消竞态）：`QUERY_CONCURRENCY=4` 个完整检索并发上限，超出排队
   `QUERY_MAX_QUEUE_SECONDS=5s` 后拒绝——`/api/search` 返回 429+`Retry-After`，聊天流
   发终端 `error` 事件（busy 文案）。**闸在检索缓存 miss 之后**，命中不占容量；
   已接受的请求永远走完整质量路径（排队优先于降级）。
5. **降级可观测**：`retrieve()` 各降级站点追加 `degraded` 标签，终日志 extra 携带
   （`LOG_FORMAT=json` 时顶层字段）；`retrieve()` 拆出 `_retrieve_uncached`，缓存命中
   不触碰流水线。

## 后果

- 正面:
  - embedding/rerank 有效并发 = key 数 × 每 key 上限（默认 8/把），429 时秒级
    failover 而非最长 31s 干等；重试带抖动，避免同拍踩踏；
  - 查询路径 provider 请求量约降 N 倍（1+N→1），摄取请求量约降 6 倍（5→32），
    实际额度消耗反而下降；缓存读写从 ~600 次连接/文档 → 1 条常驻连接；
  - 过载时排队+拒绝，杜绝"全员打折"——质量水位不随负载漂移，且降级率可通过
    `degraded` 日志聚合监控；
  - eval 检索指标前后对比无回归（GUIDE-002 流程），合批质量中性被一致性测试锁定。
- 负面:
  - 池耗尽（全 key 冷却/占满）时 embedding 抛 `KeyPoolExhausted`→`EmbeddingServiceError`
    （上传 400），rerank 走既有 fallback（有 warning 日志，非新增静默降级）；
  - 查询闸为进程级（与摄取闸、BM25 索引同层）；多 worker 时各 worker 独立计 4 个
    并发——上多 worker 前需重审（ADR-007 已记录 BM25 跨进程问题）；
  - 新增 7 个配置项，运维面略增。
- 取舍:
  - **不做**每 key RPM 滑窗预估：429 冷却+failover 已覆盖临界场景，且与 provider
    真实计数器漂移的预估只会错误排队本会成功的请求；
  - 冷却下限 1s：尊重 provider 短 Retry-After 与防止贴线重试之间取保守值；
  - 不升级到跨 provider 主备：不同 embedding 模型维度不同，不能共用 collection，
    属于另一类容灾，不在本次范围。

## 落地

  run_with_key_retry；日志只打 `****+末4位` 指纹

## 验证记录（2026-09-10）

- 全量单测 380 过 1 skip（opt-in live 一致性）；
- live 向量一致性（真实 API）：单发 vs 单条批/4 条批余弦 = 1.000（≥0.999 门禁通过）；
- eval 检索指标（`--no-llm`，12 有效例，基线 3 次 vs 改后 2 次）：MRR 0.774–0.788 →
  0.774/0.785；nDCG@5 0.701–0.717 → 0.708/0.725；Recall@5 0.750–0.778 → 0.750/0.778；
  Hit@1 0.667 持平——全部落在基线噪声区间内，无回归；eval 期间 degraded 计数 0；
- 过载演练（QUERY_CONCURRENCY=1、QUEUE=0.5s）：3 并发搜索 → 1×200 + 2×429
  （`Retry-After: 1`、busy 文案）；并发聊天流 → 终端 `event: error`（busy 文案）无 done；
- 关停：eval CLI 进程在连接 daemon 化修复后干净退出（exit 0）。
